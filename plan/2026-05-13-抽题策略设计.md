# DeepTutor 抽题策略设计 v1

更新时间：2026-05-13

## 1. 目的与边界

当前 `MockInterviewCoordinator._select_question` 只有一条路径：把用户指定的 `question_type / difficulty / position` 拼成检索 query，送进 `RAGService.search`。它**完全忽略用户画像**——即使 `profile_eval: 10/10 passed` 能识别反复弱项、持续改善和训练建议过期，这些信号都不会影响下一轮抽题。

本文档定义 V1 抽题策略：**把画像信号接入现有的 RAG 抽题路径**，不做复杂 reranker，不引入新服务，不破坏当前 CLI 和回归测试。

范围：
- 只覆盖 `interview_bank` 这一个知识库。
- 只影响 `start_interview` 路径；追问链路（followup）先不动。
- 不涉及前端 / API / 知识图谱。

## 2. 可用信号

V1 可直接取用的画像字段（都已在 `DynamicProfile` 里落地）：

| 字段 | 含义 | 使用方式 |
| --- | --- | --- |
| `repeated_weak_dimensions` | 仍然弱的维度，count ≥ 2 且最新分 < 6 | 优先抽能锻炼该维度的题型 |
| `resolved_dimensions` | 最近回升的旧弱项 | **避开**，防止反复练同一维度 |
| `recent_weak_types` | 最近低分的题型名 | 优先抽同题型 |
| `current_training_suggestion` + `status=active` | 当前仍生效的训练建议 | 作为检索 query 的额外上下文 |
| `training_suggestion_history[*].status=expired` | 已过期建议 | 不进 query |
| `dimension_trends[*].status=improving` | 正在进步的维度 | 保留少量该题型做巩固，但不是主线 |
| manifest 里的 `estimated_difficulty` | 资料难度分层（easy/medium/hard） | 按"最近平均分"做难度递进 |

## 3. 抽题决策流程

```text
start_interview(question_type, difficulty, position)
            │
            ▼
      _resolve_picker_hints(profile, recent_sessions)   ← 新增
            │
            ▼
      build_query(question_type, difficulty, position, hints)
            │
            ▼
      RAGService.search(...)
            │
            ▼
      _log_rag_provenance(...)                          ← 已有
            │
            ▼
      _filter_and_rerank(sources, hints)                ← 新增，纯 Python
            │
            ▼
      _build_question_from_rag_content(...)             ← 已有
```

三个注入点：

1. **Query 增强** (`build_query`)
   - 把 `repeated_weak_dimensions[0].dimension` 和当前有效训练建议的关键名词加到 query 文本里。
   - 不直接贴整句训练建议，只抽"焦点维度名 + 关键动词"。
   - `difficulty` 如果调用方没指定，按 `_difficulty_from_recent_scores` 推断（见第 4 节）。

2. **Source 二次过滤 / 重排** (`_filter_and_rerank`)
   - 输入：`result["sources"]`（已有 file_name / score / 查 manifest 能拿到 `estimated_difficulty / question_type`）。
   - 规则：
     - 过滤：如果命中资料的 `estimated_question_type` 属于 `resolved_dimensions` 对应的题型名，直接降权。
     - 重排：对每个 source 计算 `score += bonus(question_type 匹配 recent_weak_types) + bonus(difficulty 匹配请求)`，稳定排序。
   - 不替换 RAG 原本的 retrieval；只在 top-5 内部做二次排序。
   - 如果过滤后为空，回退到 RAG 原始顺序。

3. **难度递进** (`_difficulty_from_recent_scores`)
   - 只在 `difficulty == "medium"`（默认）且 `len(recent_sessions) >= 3` 时生效。
   - 最近 3 场平均分 ≥ 70 → 抽 `hard`；≤ 50 → 抽 `easy`；其他保持 `medium`。
   - 不跳级：不会从 `easy` 直接跳到 `hard`。

## 4. 数据结构

```python
@dataclass
class PickerHints:
    focus_dimensions: list[str]      # 来自 repeated_weak_dimensions
    focus_question_types: list[str]  # 来自 recent_weak_types
    avoid_question_types: list[str]  # 来自 resolved_dimensions 相关题型
    active_suggestion: str           # current_training_suggestion (status=active)
    suggested_difficulty: str        # 递进后的难度
    reason: str                      # 单行可观察字符串，写进 provenance log
```

`PickerHints` 全部可序列化为 JSON 放进日志，便于回放。

## 5. Fallback 行为

| 条件 | 行为 |
| --- | --- |
| profile 为空（新用户） | `PickerHints` 全空；query 和过滤器退化为当前实现 |
| RAG 命中 `fallback=True`（manifest fallback） | 跳过二次过滤，直接使用 manifest 排序 |
| 过滤后 top-k = 0 | 回退到未过滤的原 top-k |
| `_difficulty_from_recent_scores` 无数据 | 保持调用方指定的 difficulty，不推断 |
| 训练建议长度超过 80 字 | 只取前 40 字作为 query 增强 |

## 6. 验收

### 6.1 profile_eval 扩展（目标 ≥ 12 条）

新增 fixture（在 `tests/fixtures/profile_eval_cases.json`）：

- `profile-picker-focus-001`：用户反复在"论据与案例质量"低分 → `PickerHints.focus_dimensions` 命中该维度。
- `profile-picker-avoid-001`：`resolved_dimensions` 中的维度对应的题型不应出现在 `avoid_question_types` 的交集之外。
- `profile-picker-difficulty-up-001`：最近 3 场总分 75/72/80 → `suggested_difficulty == "hard"`。
- `profile-picker-difficulty-down-001`：最近 3 场总分 45/40/38 → `suggested_difficulty == "easy"`。

这 4 条断言**只验证 `PickerHints` 的派生**，不需要跑 RAG；evaluator 继续保持确定性。

### 6.2 单元测试

- `_resolve_picker_hints` 在空画像、部分画像、完整画像下的输出。
- `_difficulty_from_recent_scores` 的三个分段 + 数据不足路径。
- `_filter_and_rerank` 的稳定排序、回退、resolved 过滤。
- 查 manifest 失败时不抛出（manifest cache 已在 `_load_manifest_index` 处理）。

### 6.3 live CLI 复验（可手动）

标准脚本：

```bash
./deeptutor_cli interview start --user u1 --question-type 社会现象
./deeptutor_cli interview answer --user u1 --answer "..."
./deeptutor_cli interview profile --user u1
```

在日志里应看到：

- `picker_hints focus_dimensions=[...] suggested_difficulty=... reason=...`
- `rag_provenance kb=interview_bank ... hits=N sources=...`
- 两行日志时间先后，`picker_hints` 在 `rag_provenance` 之前。

## 7. 不做的事

- 不在 V1 引入外部 reranker（BGE-reranker、ColBERT 等）。
- 不做 embedding 级别的 profile 注入（profile 字段拼进 embedding 查询）。
- 不改 `RAGService.search` 的签名；所有策略逻辑留在 `deeptutor/agents/interview/` 里。
- 不在 V1 驱动追问（followup）；`generate_followup` 的输入先不变。
- 不把 `active_suggestion` 的原文塞给 LLM prompt，避免"按建议造题"的人为耦合。

## 8. 实施顺序

1. 新增 `deeptutor/agents/interview/picker.py`：`PickerHints` 数据类 + `resolve_picker_hints`。
2. 在 coordinator 的 `_select_question` 里调用 `resolve_picker_hints`，增强 query。
3. 新增 `_filter_and_rerank`，**先**对 `result["sources"]` 重排，**再**调 `_log_rag_provenance`，让日志反映 picker 的真实决策（落地时发现：原顺序写 "_log 在 rerank 之后" 是错的，被端到端测试 `test_select_question_calls_picker_and_reranks_sources` 抓到并修正）。
4. 在 `_select_question` 入口处加一条 `picker_hints` 日志，确保它在 `rag_provenance` 之前。
5. 扩 evaluator，增加 `picker_hints` 派生断言类型。
6. 补 4 条新 fixture + 单测。
7. 执行一次 live CLI 冒烟，观察日志；不强制跑通 live，因为 DeepSeek API 依赖 key。

这个顺序保证每一步都独立可回归，任何一步失败都可以单独回滚，不破坏当前 `profile_eval: 10/10 passed` 的状态。

## 9. 风险

- **Query 增强可能降低召回**：加多维度关键词会稀释检索匹配。缓解：只加 1 个焦点维度 + 1 个关键动词，不堆关键词；在 `_filter_and_rerank` 里保留 RAG 原始排序作为 tie-breaker。
- **难度递进判定数据不足**：`recent_sessions` 少于 3 场时不要强推，静默退化。
- **resolved_dimensions 误伤**：如果一个维度最近刚回暖就被完全屏蔽，用户没机会巩固。缓解：`avoid_question_types` 是软降权，不是硬过滤。
- **manifest 标签误判**：`estimated_difficulty` 仍有 44/62 默认 medium，过滤效果有限；这不是策略层问题，是数据层问题，在 plan 2.2 / 2.3 人工抽检和 LLM 回填阶段解决。
